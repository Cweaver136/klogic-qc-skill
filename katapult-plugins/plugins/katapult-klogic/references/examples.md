# Annotated real examples

Two real Node QC checks copied out of Katapult Pro, with the structure explained. Both happen to be the same shape — a `PROCEDURE` that computes named variables in steps, then an `AND` in `return` — and both return a boolean, but that's just these checks: a root block can resolve to any type (see the "Return value" section of `SKILL.md`).

Read these to see how item-looping, `$()` templates, `*` attributes, and procedure variables fit together in practice.

## Example 1 — complex transfer node missing a proposed pole spec

**Intent:** flag a node that (a) is Medium/Complex make-ready, (b) has a wire/arm/insulator with an `mr_note` of "Transfer", (c) is missing `proposed_pole_spec`, and (d) wasn't deselected by the applicant.

Structure:
- `var_keys`: `["isComplex","transferWireNote"]`
- `step_01` → **`isComplex`**: `OR` of two `EQUAL`s — `mr_category.*` equals `"Medium Make Ready"` **or** `"Complex Make Ready"`.
- `step_02` → **`transferWireNote`**: `OR` of three `FIND`s. Each `FIND` takes a photofirst category turned into a list (`LIST_VALUES` of `job.photos.$(main_photo_id).photofirst_data.wire` / `.arm` / `.insulator`) and, with `item_key:"wire"`, finds the first item whose `wire.mr_note` `INCLUDES` `"Transfer"`.
- `return`: `AND` of — `isComplex`, `NOT_EXISTS(node.attributes.proposed_pole_spec)`, `transferWireNote`, and `NOT_EQUAL(node.attributes.customer_directive.*, "Deselected by Applicant")`.

Things to notice:
- The `return` `AND` uses `arg_01, arg_03, arg_04, arg_05` — a gap at `arg_02` left over from editing. Harmless for a chainable op. When *you* generate, use contiguous keys.
- The same per-item test is reused across three `FIND`s with the same `item_key` — fine, since each loop scopes its own `wire`.
- A `FIND` returns the item or `undefined`; used inside `AND`, it reads as truthy/falsy ("did we find a transfer note?").

## Example 2 — midspan over a railroad, on a complex node

**Intent:** flag a complex node (not deselected) that has a section midspan measurement recorded as `over` a `"Railroad"`.

Structure:
- `var_keys`: `["nodeConnections","sectionMainPhotos","isComplex"]`
- `step_01` → **`nodeConnections`**: `GET_FROM(connection_lookup, node_id)` — this node's connections.
- `step_02` → **`sectionMainPhotos`**: `MAP` over `nodeConnections` (`item_key:"connection"`); for each, `MAP` over `connection.sectionKeys` (`item_key:"sectionKey"`) and `FIND` the section photo whose `association` equals `"main"`.
- `step_03` → **`isComplex`**: same Medium/Complex `OR` as example 1.
- `return`: `AND` of — a nested `FIND`/`FIND`/`FIND` drilling `sectionMainPhotos` → `connection` → the midspan item whose `midspan.over` equals `"Railroad"`; `isComplex`; and `NOT_EQUAL(customer_directive.*, "Deselected by Applicant")`.

Things to notice:
- **Nested item scopes:** `connection`, `sectionKey`, `midspan`, `photoKey` are each a distinct `item_key`; inner blocks freely read outer items (`connection.connId`, `connection.sectionKeys`) while working with the current inner one.
- **Templates driven by loop items:** `$(sectionKey)`, `$(connection.connId)`, `$(photoKey)` all resolve from the enclosing loop's injected item data.
- **`LIST_KEYS` vs `LIST_VALUES`:** keys when you need the id (to feed back into a `$()` template), values when you need the item objects.


## Example 3 — annotation height must match the lowest low-power marker (nesting + traces + formatting)

**Intent:** flag a node (return TRUE) when the height called out in the node's PPL annotation doesn't match the actual lowest low-power marker on the main photo. A "low-power marker" is a wire owned by `PPL Company` with a trace `cable_type` of `Secondary`/`Neutral`/`Service`, **or** a `PPL Company` `riser` equipment marker.

This is the reference case for anything touching `photofirst_data`. It exercises: the category-keyed `_children` tree, top-level height sourcing, trace lookups for company/cable type, the `mr_move` + round height formula, and formatting a height to `FT'-IN"` to contains-match against free-text prose. See `photofirst-markers.md` for the underlying rules.

Structure (`PROCEDURE`, `var_keys` `["lpHosts","lowest","feet","rem","heightStr"]`):
- `step_01` **lpHosts** — `CONCATENATE_LISTS` of four `FILTER`s over the **top-level** markers, since height lives on the top-level marker: top-level low-power wires; insulators whose `_children.wire` has a low-power wire (`SOME`); arms with a low-power wire anywhere beneath (`_children.wire` plus `_children.insulator.*._children.wire`, gathered with `MAP`+`FLATTEN_LIST`); and PPL `riser` equipment.
- `step_02` **lowest** — `MIN_LIST` of `MAP(lpHosts, ROUND(FALLBACK(measured,manual) + FALLBACK(mr_move,0)))`. Height read off the surviving **host**, not the nested wire.
- `step_03`–`step_05` **feet / rem / heightStr** — `FLOOR(lowest/12)`, `lowest − feet·12`, then `CONCATENATE(feet,"'-",rem,"\"")` → e.g. `27'-3"`.
- `return` — `IF_ELSE(EXISTS(lowest), EXCLUDES(annotation, heightStr), $FALSE)`: flag when the annotation doesn't contain that height; never flag when there are no low-power markers.

Things to notice:
- **`_children` is category-keyed:** `host._children.wire`, `arm._children.insulator.*._children.wire` — never `LIST_VALUES(_children)`.
- **Height off the top-level host:** nested insulators/wires carry no height, so the `FILTER`s keep top-level markers and `MAP` reads the height from them.
- **Traces:** company and cable type come from `job.traces.trace_data.$(w._trace)`; equipment carries `equipment_type` on the marker itself.
- **Contains-match, not equality:** `EXCLUDES(annotation, heightStr)` tolerates surrounding prose; the `IF_ELSE`/`EXISTS` guard prevents false flags on empty results. The `FT'-IN"` format must match the annotation byte-for-byte.


## Example 4 — proposed slack comm cable overtop an existing full-tension comm cable (Section check)

**Intent:** flag a **Section** (return TRUE) when its midspan has a *proposed, slacked* communication cable sitting physically higher than an *existing, full-tension* communication cable. This is the reference case for **entity choice**: the request said "if any *connection* has…", but a Section check is cleaner — it exposes a single `main_photo_id` (the midspan photo), so there's no looping across a connection's sections to find main photos, and each span point is evaluated on its own. See `datasets/sections.md`.

It also shows the **marker-vs-trace split** confirmed in this model: `wire_tension` (`Full` / `Slack`) is read off the **marker** (`w.wire_tension`), while `cable_type` and `proposed` are read off the **trace** (`job.traces.trace_data.$(w._trace)....`). Don't assume where a field lives — confirm per model.

Structure (`PROCEDURE`, `var_keys` `["midWires","proposedSlackCom","existingFullCom"]`):
- `step_01` **midWires** — `LIST_VALUES(job.photos.$(main_photo_id).photofirst_data.wire)`: this section's midspan wire markers.
- `step_02` **proposedSlackCom** — `FILTER` (`item_key:"w"`) keeping comm wires (`OR` of trace `cable_type` = `Telco Com` / `Fiber Optic Com` / `CATV Com`) that are `wire_tension` = `Slack` (marker) **and** `IS_TRUE(...proposed)` (trace).
- `step_03` **existingFullCom** — same comm test, `wire_tension` **not** `Slack` (`NOT_EQUAL`, so an absent/unset tension counts as full), `IS_FALSE(...proposed)`.
- `return` — nested `SOME`/`SOME`: is any proposed-slack wire's height greater than any existing-full wire's? Height per wire is `FALLBACK(_measured_height, _manual_height)`. `true` = flag.

Things to notice:
- **Entity choice is the first decision.** The same check as a Connection would have to loop `sections` → find each main photo → gather wires; the Section source reduces `step_01` to one `LIST_VALUES`. Confirm the entity before building.
- **Field location is per-model:** `wire_tension` off the marker, `proposed`/`cable_type` off the trace. Mixing these up pastes fine and reads wrong.
- **"Overtop" = height comparison:** two `SOME`s with distinct `item_key`s (`p`, `e`) form an any-over-any test; each height is `FALLBACK(_measured_height, _manual_height)`. Add `mr_move` only if the check should reflect post-MR positions.
- **Comm set is explicit:** `Telco Com` / `Fiber Optic Com` / `CATV Com`. `Com Drop` is deliberately excluded — add it if service drops should count.
